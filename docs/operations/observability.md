# Observability and support diagnostics

## Operating model

SimProof emits local, structured operational signals for one self-hosted deployment.
The signals help distinguish configuration, migration, persistence, provider, runner,
and scientific-verification outcomes. They are not teacher-content analytics and are
not a substitute for verification evidence.

Every signal passes the shared strict runtime schema before a sink receives it. A
signal contains only:

- schema version, occurrence timestamp, severity, component, and registered event ID;
- an optional registered stable error ID;
- optional server-generated request, generation-run, attempt, and simulation IDs; and
- allowlisted state, verdict, status, attempt, queue, resource, and retry fields.

The schema rejects unknown fields. It has no arbitrary message, header, URL, path,
environment, exception, or content field. Raw causes may remain on an in-process error
object for control flow, but they never enter a signal or diagnostic bundle.

HTTP request IDs are generated by SimProof rather than trusted from a caller. A
generation run keeps the same `runId` as it crosses persistence, providers, runner
execution, and trusted verification. The server returns its request ID in the safe
response header so an operator can match a reported failure to local diagnostics.

## Stable error IDs

Stable IDs are defined by the application-owned operational error registry. They are
safe classifications such as `provider.authentication-failed`,
`runner.execution-failed`, and `migration.failed`; they are not provider messages or
exception text. A new component must register an ID before emitting or persisting it.

The diagnostic command reports only registry-known IDs. If a damaged or older database
contains another value, the bundle increments `unregisteredCount` and omits the value.

Scientific finding IDs remain part of immutable verification evidence. An operational
error ID describes why a workflow could not proceed; it must not replace or reinterpret
a scientific finding or verdict.

## Health and readiness

`GET /health` is a dependency-free liveness check. It does not open the database,
inspect artifacts, invoke the runner, or contact a provider.

`GET /ready` checks configuration, the exact checksummed migration state, database
access, artifact-root safety/access, and runner availability whenever the launcher
binding is configured. The supported Compose profile always configures that binding,
including seed-only mode. A runner probe checks only local daemon/image availability;
it does not execute generated code. Health and readiness never invoke paid model
operations.

A readiness failure returns HTTP `503` and one safe stable ID. It never returns a
filesystem path, endpoint, environment value, database message, runner output, or
credential. A deployment with no provider credentials remains eligible for readiness
and the bundled seed library, but its configured local launcher must still be
available. Provider absence never triggers a provider call or readiness failure.

## Local signals and metrics

Local signals use private NDJSON files beneath the configured diagnostic log root.
Each event and file has a hard byte limit, and the store rotates through a configured
maximum file count. The oldest rotated file is removed when the count bound is reached;
there is no age-based retention policy. Errors are never sampled out. Diagnostic readers
revalidate every retained signal and discard malformed entries instead of copying raw
bytes.

Configure the optional root and retention bounds with
`SIMPROOF_DIAGNOSTIC_LOG_ROOT`, `SIMPROOF_DIAGNOSTIC_LOG_MAX_BYTES`, and
`SIMPROOF_DIAGNOSTIC_LOG_FILES`. The effective root must be an absolute local path that
does not equal, contain, or sit beneath the metadata database path or artifact root.
Diagnostic bundles disclose only whether each setting was explicitly supplied, never
its value.

Local metrics have fixed, low-cardinality dimensions:

- generation state transitions and terminal classes;
- verification verdicts;
- provider and runner failure classes;
- queue depth and generation/repair attempt counts; and
- isolated-runner resource rejections.

Metrics never use request, run, attempt, simulation, provider-request, or Codex-thread
IDs as labels.

## External telemetry

External telemetry is disabled by default. Setting an endpoint alone does not enable
it. Export requires both:

```env
SIMPROOF_TELEMETRY_ENABLED=true
SIMPROOF_TELEMETRY_ENDPOINT=https://collector.example.edu/v1/metrics
```

The default configuration creates no exporter and performs no telemetry network call.
When explicitly enabled, only fixed metric names, numeric aggregates, fixed failure or
state classifications, and the application version may leave the deployment. Prompts,
generated or artifact content, correlation IDs, titles, findings content, paths,
environment values, credentials, cookies, provider responses, and reasoning are
excluded.

Any OpenTelemetry/OTLP transport must remain behind the shared exporter port and be
constructed only in the enabled branch. Do not use automatic instrumentation or a
dependency that starts remote export when imported.

External diagnostic-bundle transmission is a separate capability. The operator command
in this release creates a local file only and performs no upload.

## Creating a diagnostic bundle

Build the production command, then choose a new private destination:

```sh
pnpm build
pnpm diagnostics -- create --output ./simproof-diagnostics.json
```

Local redacted signals are a separate explicit category:

```sh
pnpm diagnostics -- create \
  --output ./simproof-diagnostics-with-logs.json \
  --include logs \
  --max-log-events 200
```

The command accepts only the `logs` category. It refuses stdout, unknown categories,
duplicate options, unsafe filenames, symlink destinations, and existing output files.
The resulting JSON file is created with mode `0600`, is size bounded, and is validated
against the strict bundle schema before writing. The command prints only fixed success
or failure text; it never prints the bundle or destination contents.

The bundle allowlist contains:

- SimProof component, Node, runner-protocol, and database-schema versions;
- configuration presence/enabled booleans, never configuration values;
- migration version/status without SQL, paths, or applied timestamps;
- the safe readiness result;
- aggregated registry-known recent stable error IDs and an unknown-ID count; and
- strictly parsed, redacted, bounded signals only after `--include logs`.

It always declares the excluded categories: environment values, credentials,
authentication records, cookies, prompts, generated content, artifact content,
provider responses, and reasoning. No option enables those categories.

The migration inspection is read-only. It does not create a missing database, apply a
migration, rewrite a journal, repair an artifact, start the application, or contact a
provider. A missing, unsafe, or incompatible data source is reported through safe
status fields.

## Support handling

Treat a diagnostic bundle as private operational data even though it is redacted. It
may contain random request, simulation, run, or attempt identifiers and deployment
version information. Review it before sharing, transfer it through an operator-approved
channel, and remove the local copy when it is no longer needed.

Do not add a raw environment dump, database copy, artifact archive, prompt export,
container output, provider response, or exception stack to a support bundle. Use the
separate authenticated teacher export or protected backup workflows for their defined
purposes; neither is a diagnostic attachment.
